## Procedimiento de workers y conciliación que debe homologarse

1. Web/API no inicia envío de correos, importación logística ni jobs de conciliación nueva. Backend/worker tiene secretos separados; Auth SMTP pertenece a Supabase. Cada worker registra heartbeat con nombre/version y contadores, sin email, tokens, cuerpos, direcciones o respuesta cruda.
2. Worker de reservas corre en host/scheduler persistente con intervalo de 60 s como objetivo; medir drift. La función existente serializa cancelación/expiración y repone componentes una sola vez. Configurar alarmas si hay atraso >2 ciclos. No tener dos mecanismos de compensación diferentes.
3. Conciliación periódica toma IDs de pagos persistidos, consulta la API autenticada y usa `reconcilePayment`, igual que webhook. Necesita cubrir también holds/rechazados/tardíos y no depender de un único webhook o retorno del navegador. Intervalo/retención/quotas deben homologarse con la cuenta; no se programó ningún job Cloud.
4. Logística usa claim con `SKIP LOCKED`, identidad estable por pedido/bulto y lock de pedido. Retries únicamente para rechazo explícito 429, máximo existente 3 intentos. Claim abandonado (>2 min), duplicado, timeout y 5xx requieren conciliación humana; no repetir el import a ciegas. Un hold posterior al inicio de un request no puede deshacer un envío ya en vuelo: alertar y resolver con el operador.
5. Email usa claim y envelope persistido **antes** del transporte. Aceptación de Resend y acknowledgement se guardan juntos en SQL. Reintentos mantienen clave/bytes; a 23 h, máximo de intentos o resultado incierto se pasa a revisión. Claim abandonado (>5 min) también va a revisión. No resetear `prepared_at`, generar otra clave o enviar otra copia para solucionar un timeout.
6. Webhook de Resend debe capturar raw bytes antes de JSON, verificar Svix, persistir mínimo y responder tras commit. Por ahora el handler preparado no está registrado. Los hechos se guardan independientemente del orden de llegada; puede haber recibo antes del acknowledgement. Consultar por `provider_id`; una entrega no borra un bounce/complaint recibido antes o después. Resend mantiene supresión; no retirarla automáticamente.
7. Si falla una publicación/job: detener el componente afectado, preservar evidencia/claim/estado, evaluar alcance y pedir decisión para reparación/restauración/reenvío. No desplegar una versión de backend que espere migraciones inexistentes ni iniciar workers viejos sobre contratos nuevos.
